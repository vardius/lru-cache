These numbers measure the cache alone: keys are made before the timer starts, so what's left is hashing, locking,
and keeping the order of use. Every benchmark uses a cache of 1,024 entries, string keys and byte slice values.
The parallel ones run 16 goroutines at once: their time is wall time per call across all of them, so it measures throughput.

## v1 against the untagged version

Both versions ran on the same harness, with the same keys, values and order of calls.
The untagged version counts bytes, so its budget was one byte more than 1,024 values: it holds as many entries.

The untagged version kept entries in a `container/list` and found them with a Go map. Every new key allocated a list
element and an entry, and evicting deleted from the map and inserted again. v1 keeps entries in one slice and finds
them with an index of its own: a new key in a full cache takes the evicted entry's place in the slice, and trades
one slot of the index for another, with no allocation.

A miss costs a little more than before. The index hashes keys with `hash/maphash`, outside the lock, where a Go map
hashes inside its own lookup. The same index is what makes evicting cheap, and keeps the hashing out of the lock.

<Aside title="Where the allocations go">
`New` allocates three times: the cache, room for every entry, and the index. With keys of strings, numbers or structs
of them, nothing allocates after that:
`Get`, `Set` and `Delete` work in that room, and `Set` on a full cache reuses the evicted entry's place.
A Go map in its place can grow while the number of entries stays the same: every eviction deletes a key and inserts
another, and the slots deleted keys leave behind can fill the map until it grows. The index is never more than half
full and leaves no such slots, so it never grows.
</Aside>

## Run them yourself

From a clone of the repository:

```sh
go test -run '^$' -bench . -benchmem
```

To compare two versions, run each a few times and compare with [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat):

```sh
go test -run '^$' -bench . -count 10 > new.txt
benchstat old.txt new.txt
```

The allocation counts are also enforced by tests: `TestAllocations` fails if a call allocates more than it should.
